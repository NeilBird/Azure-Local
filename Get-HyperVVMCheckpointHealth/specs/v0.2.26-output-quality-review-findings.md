# Get-HyperVVMCheckpointHealth Output Quality Review Findings Specification

## Status

- **Source review:** `Get-HyperVVMCheckpointHealth` 0.2.26
- **Review dataset:** `CheckpointAudit_2026-07-27_094459Z`
- **Specification status:** Implemented for 0.2.27
- **Change type:** Reporting and evidence-quality refinement
- **Target release:** 0.2.27

## Purpose

This specification defines reporting improvements identified during an in-depth review of a production 0.2.26 audit containing 55 VM results. The review assessed output quality, recommendation quality, evidence traceability, collection completeness, cross-artifact consistency, and HTML usability.

The reviewed verdict and recommendation logic was sound. All 21 `INVESTIGATE` results had explicit drivers, and every numeric claim for unresolved events, orphan files, stale attached AVHDX layers, and stale named snapshots reconciled with the underlying TXT and CSV evidence. No collection failure, unsupported verdict, unsafe recommendation, or count inconsistency was found.

The requirements below improve the self-sufficiency and clarity of individual artifacts without changing the validated assessment model.

## Goals

1. Give standalone TXT reports the same effective Replica guardrail evidence available in HTML.
2. Distinguish raw event classification from final verdict significance in event CSVs.
3. Make a standalone `NOT FOUND` TXT report operationally complete.
4. Make root checkpoint hierarchy explicit instead of rendering an ambiguous blank parent.
5. Keep support-escalation guidance specific to the evidence that drove the verdict.

## Non-Goals

- Change checkpoint, AVHDX, Replica, HRL, VSS, CSV free-space, or event assessment thresholds.
- Change verdict precedence or the meaning of `HOLD STATE`, `INVESTIGATE`, `OK`, `NOT FOUND`, or `ERROR`.
- Reclassify event IDs or alter operation-recovery correlation.
- Treat the optional Hyper-V-VMMS/Analytic channel as required evidence.
- Authorize automatic remediation, merge, deletion, rename, migration, restart, or HRL modification.
- Remove existing event CSV columns or break existing 0.2.x consumers.

## Validated Baseline

The implementation must preserve these 0.2.26 behaviors:

- Numeric `Why flagged` claims are derived from collected evidence.
- Event `18012` can drive checkpoint-reliability investigation when unresolved and VM-attributed.
- Event `19090` can be retained as context without driving the verdict when recovery or absence of persistent residue supports that interpretation.
- Historic event coverage limitations name incomplete node/channel scopes and state that absence of an event is not proof that no rollback occurred.
- The optional Analytic channel is reported as diagnostic-depth guidance only.
- Base VHDX layers report `Checkpoint stale = n/a (base)`.
- Attached VHD chain evidence uses the compact nine-column table, contained horizontal scrolling, and collapsed full-path evidence.
- Reporting remains diagnostic and read-only.

## Functional Requirements

### FR-1: Replica Evidence Parity in TXT

When Hyper-V Replica is enabled, the per-VM TXT report must include a structured assessment table equivalent to the HTML **Hyper-V Replica details** table.

The table must contain:

| Signal | Required observed value | Required guardrail/context | Required assessment |
|---|---|---|---|
| Product state and health | State and health | Authoritative `Get-VMReplication` evidence | Product severity |
| Relationship | Mode | Primary and replica servers | Context |
| Replication cadence | Frequency in seconds | Used to calculate relationship-aware limits | Context |
| Monitoring window | Monitoring interval | `Get-VMReplicationServer` monitoring interval | Context |
| Last replication | UTC timestamp and age in minutes | Effective maximum age in minutes | Within limit, Advisory, Concern, or Unavailable |
| Average replication size | Human-readable bytes | Workload baseline | Context |
| Pending replication data | Human-readable bytes | Effective maximum pending bytes | Within limit, Advisory, Concern, or Unavailable |
| Average replication latency | Seconds | Effective maximum latency | Within limit, Advisory, Concern, or Unavailable |
| Measured replication cycles | Successful count, missed count, and missed rate | Maximum missed rate or count/rate guardrails | Within limit, Advisory, Concern, or Unavailable |

Requirements:

- Values and guardrails must come from the same typed Replica assessment object used by HTML.
- Bytes must be rendered with human-readable units while preserving exact numeric values in the existing raw collection section.
- UTC timestamps must end in `Z`.
- Missing measurements or server settings must render as `Unavailable`, not zero unless zero was actually measured.
- Product health/state must remain authoritative; measurement-only concerns must not be described as product-health failures.
- The recommendation must name each breached effective limit or point directly to this table.

### FR-2: Event CSV Classification and Disposition

VM event CSVs must distinguish the event catalog classification from whether the row drives the VM verdict.

Append these columns after the existing columns:

| Column | Values | Meaning |
|---|---|---|
| `EventClassification` | `High-signal`, `Low-signal`, `Corroborating`, `Informational` | Static or contextual classification of the event evidence |
| `VerdictDriver` | `True`, `False` | Whether this row contributes to the final VM verdict |
| `RecoveryDisposition` | `Unresolved`, `ConfirmedRecovered`, `ApparentlyRecovered`, `ContextOnly`, `NotApplicable` | Correlation result used by assessment logic |
| `DispositionReason` | Free text | Concise reason for the disposition |

Compatibility requirements:

- Existing columns and their order must remain unchanged.
- New columns must be appended, not inserted.
- `Concern` must remain for 0.2.x compatibility but must be documented as event-level classification, not final verdict significance.
- Marker rows must use `EventClassification=Informational`, `VerdictDriver=False`, `RecoveryDisposition=NotApplicable`.
- An unresolved VM-attributed `18012` that drives `INVESTIGATE` must use `VerdictDriver=True` and `RecoveryDisposition=Unresolved`.
- A `19090` retained as low-signal context must use `VerdictDriver=False` and an appropriate recovery disposition.
- Node-wide CSVs may omit VM-specific disposition columns only if their schema is explicitly documented as node context. Prefer schema parity with blank or `NotApplicable` values.

### FR-3: Self-Contained `NOT FOUND` TXT Report

A `NOT FOUND` TXT report must be useful when shared without the fleet HTML.

It must include:

- Input VM name.
- Cluster name.
- Statement that the VM was not found on any cluster node.
- Statement that the VM was not fully assessed and must not be treated as healthy from this result.
- Confirmation that event collection was not attempted for the missing VM.
- Path to the marker event CSV.
- Guidance to verify spelling, naming differences, and cluster ownership.
- A ready-to-edit rerun command using the confirmed VM name.
- A statement that no checkpoint, disk, Replica, VSS, or event conclusion was produced for that VM.

Example intent:

```text
RESULT: NOT FOUND - this VM was not fully assessed. Do not treat it as healthy based on this report.
Verify the VM name and cluster, then rerun:
Get-HyperVVMCheckpointHealth -VMName '<confirmed-name>' -OutputPath '<folder>'
```

The marker CSV and fleet HTML must use the same reason and cluster identity.

### FR-4: Explicit Root Checkpoint Parent

The named-checkpoint `Parent` column must distinguish a root checkpoint from missing collection data.

Requirements:

- If the checkpoint has no parent and parent collection succeeded, render `n/a (root)`.
- If parent information could not be collected, render `Unavailable`.
- If a parent exists, render its checkpoint name unchanged.
- Apply the same display semantics to HTML and TXT.
- Preserve the underlying `Parent` data property for automation compatibility.
- Do not confuse named-checkpoint parentage with VHD `ParentPath`; both remain separate evidence concepts.

### FR-5: Driver-Specific Escalation Guidance

Support-escalation guidance must be selected from the actual investigation drivers.

Required behavior:

| Driver | Primary routing | Support escalation condition |
|---|---|---|
| Unresolved `18012` only | Backup/checkpoint job owner | Persistent failures after owner review, or separate durable Hyper-V/storage evidence |
| Replica product health/state | Replica owner | Persistent abnormal state after connectivity/capacity/configuration review |
| Replica measurement breach | Replica owner | Breach persists across the next monitoring interval after owner review |
| HRL cadence concern | Replica owner | Queue remains beyond cadence with corroborating Replica degradation after owner review |
| Stale attached layer or snapshot | Backup/storage owner | Persistent merge failure, durable artifact, or owner rules out its component |
| Orphan without confirmed historic signature | Backup/storage owner | Purpose cannot be established or durable artifact cannot be safely resolved |
| Confirmed historic fork-commit/rollback | Backup vendor and Microsoft Support | Immediate recovery/chain-validation guidance appropriate |
| Incomplete collection state | Collection owner, then relevant component owner | Escalate only after required evidence remains unavailable or risk requires specialist review |

Requirements:

- Replica-only findings must not lead with fork-commit language.
- Event-only findings must explicitly state that the event does not identify a disk requiring manual action.
- Orphan, checkpoint, and chain findings must retain the prohibition against blind file changes.
- HRL guidance must explicitly prohibit modifying or deleting HRL files based on the report.
- Generic Microsoft Support language may remain in a reference or final fallback section, but must not obscure the primary driver-specific action.

## Cross-Artifact Consistency Requirements

For every VM result:

1. TXT, HTML, telemetry, and CSV artifacts must agree on VM identity and cluster identity.
2. Fleet verdict totals must equal the result-object totals recorded in telemetry.
3. Each non-`OK` result must expose an explicit reason and actionable next step.
4. Numeric driver counts must agree with their evidence sections and CSV rows.
5. Incomplete coverage must never be represented as complete negative evidence.
6. `NOT FOUND` and `ERROR` results must be excluded from fully assessed totals.
7. No artifact may imply that an optional Analytic-channel state changes verdict confidence.

## Reporting and Accessibility Requirements

- Preserve the current self-contained HTML design with no external dependencies.
- Preserve desktop and mobile containment; no page-level horizontal overflow.
- Keep long VM, checkpoint, disk, and path values wrap-safe.
- Keep primary evidence compact and move full paths to disclosures where appropriate.
- Use text labels in addition to color for every concern, advisory, and verdict.
- Empty cells must not represent meaningful states when a label such as `n/a (root)`, `n/a (base)`, or `Unavailable` is available.

## Acceptance Criteria

### AC-1: Replica TXT Evidence

Given a Replica relationship with product health `Normal`, pending data `5.72 GB`, and an effective pending-data maximum of `1.78 GB`, the TXT report must show:

- Product state/health as healthy.
- Pending data as `5.72 GB`.
- Effective maximum as `1.78 GB`.
- Pending-data assessment as `Concern`.
- Other within-limit measurements as within limit.
- A Replica-owner recommendation that does not imply checkpoint-chain corruption.

### AC-2: Critical Replica State

Given `WaitingForStartResynchronize / Critical`, last replication age `55,550.8 min`, effective maximum `180.0 min`, and missed rate `100.00%` against `10.00%`, TXT and HTML must display those comparisons and route the action to the Replica owner.

### AC-3: Resolved Low-Signal Event CSV

Given a VM-attributed `19090` event that does not drive the verdict:

- `Concern` may retain its compatibility value.
- `EventClassification` must be `Low-signal` or `Corroborating` as appropriate.
- `VerdictDriver` must be `False`.
- `RecoveryDisposition` must explain whether it was recovered or retained as context.
- The final verdict must not be changed solely by that row.

### AC-4: Unresolved `18012` Event CSV

Given two unresolved VM-attributed `18012` events:

- Both rows must use `VerdictDriver=True`.
- Both rows must use `RecoveryDisposition=Unresolved`.
- TXT and HTML must report exactly two unresolved events.
- The recommendation must route first to the backup/checkpoint job owner.

### AC-5: `NOT FOUND`

Given an input VM absent from every cluster node:

- Telemetry must count one `NOT FOUND` and exclude it from fully assessed VMs.
- TXT must contain the incomplete-assessment warning and rerun command.
- CSV must contain one informational marker row and state that event collection was not attempted.
- HTML must show `NOT FOUND`, not `OK` or `ERROR`.

### AC-6: Root and Nested Checkpoints

Given one root named checkpoint and one child checkpoint:

- Root displays `n/a (root)` in `Parent`.
- Child displays the root checkpoint name.
- Attached VHD parent paths remain in the separate chain-path evidence.

### AC-7: Incomplete Historic Coverage

Given an orphan whose historic search window predates retained required logs:

- TXT and HTML must state that coverage is incomplete.
- Each insufficient node/channel scope must be listed.
- The oldest available history must be shown where known.
- The report must state that absence is not proof that no rollback occurred.
- Positive orphan evidence may still drive `INVESTIGATE`.

### AC-8: Artifact Reconciliation

For a multi-VM fixture:

- Every TXT has exactly one matching VM event CSV.
- All CSVs import successfully.
- Telemetry verdict totals match HTML summary totals and VM cards.
- Every numeric `Why flagged` claim matches source evidence.

## Test Plan

### Unit Tests

- Replica assessment table formatting in TXT for healthy, advisory, concern, critical, and unavailable measurements.
- Event CSV disposition mapping for unresolved, confirmed-recovered, apparently-recovered, context-only, and marker rows.
- `NOT FOUND` TXT content and marker CSV schema.
- Root, child, and unavailable checkpoint-parent display values.
- Driver-specific recommendation selection for every driver category and mixed-driver combinations.

### Regression Tests

- Preserve all existing 0.2.26 verdict and staleness tests.
- Preserve existing event CSV columns and append new columns.
- Preserve `n/a (base)` for base VHDX checkpoint status.
- Preserve compact attached-chain HTML and collapsed path evidence.
- Preserve incomplete historic-coverage qualification.
- Preserve optional Analytic-channel behavior.

### Integration Tests

- Generate a mixed fleet containing `OK`, `INVESTIGATE`, `HOLD STATE`, `NOT FOUND`, and `ERROR` results.
- Parse every TXT and CSV artifact and reconcile counts with HTML and telemetry.
- Import the generated event CSVs under Windows PowerShell 5.1.
- Validate the self-contained HTML in desktop and mobile browser viewports.
- Confirm no body-level horizontal overflow and no incoherent text overlap.

## Release and Compatibility

- Deliver in a new patch version; do not replace the published 0.2.26 assets.
- Document appended CSV columns and clarify the legacy meaning of `Concern`.
- Regenerate the synthetic HTML example after renderer changes.
- Rebuild the ZIP only after all included files are final.
- Repin the setup script to the rebuilt ZIP SHA256.
- Run the full redirected Windows PowerShell 5.1 Pester suite before publication.
- Extract the release ZIP into a clean directory and verify manifest import and exported command version.

## Definition of Done

This specification is complete when:

- All functional requirements and acceptance criteria are implemented and tested.
- TXT Replica evidence independently substantiates each Replica recommendation.
- Event CSV rows distinguish raw classification from verdict significance.
- `NOT FOUND` TXT reports are self-contained.
- Root checkpoint parents display `n/a (root)`.
- Escalation guidance is driver-specific.
- Existing assessment outcomes remain unchanged for equivalent evidence.
- Full Windows PowerShell 5.1 tests pass with no failures.
- Generated HTML passes desktop and mobile layout checks.
