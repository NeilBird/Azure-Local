# Azure Local Update Management - CI/CD Pipelines

This repository runs **Azure Local (Azure Stack HCI) update management** at fleet
scale, powered by the [`AzLocal.UpdateManagement`](https://aka.ms/AzLocal.UpdateManagement)
PowerShell module. The pipelines assess update readiness, apply updates, and
monitor in-flight update runs across your clusters.

## What's in this repo

- **Pipelines:** `__WORKFLOW_SUBPATH__` (platform: **__PLATFORM__**)
- **Configuration:** `config/`
- **Turnkey refresh script:** `Update-Module-And-Pipelines.ps1` (repo root)
- **Candidate-testing helper:** `DevChannel/Apply-ModuleDevelopmentChannel.ps1`

## Refresh after a new module release

When a new `AzLocal.UpdateManagement` version is published, run the turnkey
script from this consumer repository's root. It normally selects the latest
listed Gallery version, installs/imports it locally, and refreshes the managed
pipeline and configuration files while preserving supported
`BEGIN/END-AZLOCAL-CUSTOMIZE` edits. Start with local review:

```powershell
.\Update-Module-And-Pipelines.ps1 -NoPush
```

Review the diff, then commit and push the changes. Without `-NoPush`, the script
stages managed files, commits, and pushes changes on the currently checked-out
branch. It does not create or switch branches, and it does not change an existing
pipeline runtime pin. `-RequiredVersion <version>` selects an exact Gallery
version for the local refresh; it does not set the remote pin.

## Candidate testing: what DevChannel means

The development channel is a **temporary version pin**, not a separate Git branch,
repository, package feed, or copy of the module's source code. `DevChannel/` is
only the folder containing the helper. Both helpers update files in **this same
consumer repository**, not the upstream module-development repository.

| Purpose | Normal updater | Development-channel helper |
|---|---|---|
| Select local module and templates | Latest listed by default, or an exact version | Exact candidate, or latest listed with `-Disable` |
| Refresh managed repository files | Yes | Yes, by calling the normal updater |
| Manage pipeline runtime pin | No; existing pin is unchanged | Yes: sets/removes the GitHub variable; prints required ADO commands |
| Commit and push refreshed files | By default; use `-NoPush` for review | Same, through the updater; use `-NoPush` for review |

After the candidate is published to Gallery and resolves by exact version
(it may remain unlisted), run **only the development-channel helper**:

```powershell
.\DevChannel\Apply-ModuleDevelopmentChannel.ps1 -RequiredVersion 0.9.40 -NoPush
```

It validates the candidate, calls the updater to install/import that version and
refresh its templates, then configures the runtime pin. There is normally no need
to run the updater separately first. Review, commit, and push the refreshed files
before running candidate validation.

**`-NoPush` is not a read-only preview.** The GitHub repository variable still changes
after a successful refresh. `REQUIRED_MODULE_VERSION` applies repository-wide to
workflows that read it, not just to the checked-out branch; a supported manual
version input can override it. Use a separate test repository for isolation and
keep scheduled/state-changing workflows disabled until deliberately approved.
For ADO, run the printed variable-group command separately; a shared group can
affect multiple linked pipelines. Neither helper creates an isolated environment.

After acceptance and listing, return to normal latest-listed resolution:

```powershell
.\DevChannel\Apply-ModuleDevelopmentChannel.ps1 -Disable -NoPush
```

This refreshes latest-listed templates before removing the GitHub pin (or printing
the ADO removal command). It is a template refresh, not a Git history rollback;
review and commit the resulting diff. Rollback safeguards may stop on removed
customization sections or request confirmation to remove newer local module versions.
